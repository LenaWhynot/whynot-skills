# Большие исходники: скачивание и сеть

Справочник навыка `process-reel-cut`. Читать, только если исходники лежат в облаке
и весят десятки гигабайт.

## Перемотка по HTTP ВРЁТ — резать только с локального файла

Самая дорогая ошибка этой сессии: весь отбор шотов оказался недействительным, потому что
`ffmpeg -ss <t> -i <http-url>` попадает **не туда**. На 4,7 ГБ VBR-файле кадр по одному
и тому же тайм-коду из сети и из локального прокси — **разные моменты**, расхождение
десятки секунд. Индекс (moov) лежит в конце файла, по сети ffmpeg его толком не читает
и оценивает позицию по битрейту.

Контрольный опыт, который это установил: на ЛОКАЛЬНОМ файле прокси и 4K по одному
тайм-коду совпадают кадр в кадр. Значит врёт не прокси-конвейер, а сетевая перемотка.

**Правило: анализировать можно по сети, РЕЗАТЬ — только с файла на диске.**
Прежний вывод «byte-range на 0,4–2,7%, ничего не храним» держится только для СБОРА
признаков сплошным чтением. Для извлечения кусков файл надо скачать — кусками
с явным `Range` (НЕ `-C -`, см. ниже), с многоточечной проверкой и сплошным декодом.

Если скачать нельзя — единственный честный вариант, `-ss` ПОСЛЕ `-i` (точная перемотка
декодированием с начала), но это тянет весь файл ради одного куска.

⚠️ Признак беды в логе: `Unexpected offset: expected …, got 0` и `partial file`.
Появились — значит поток рвался, тайм-коды под подозрением.

## ⚠️ `curl -C -` ВМЕСТЕ с `-r` тихо портит файл — так качать нельзя

Самая дорогая ошибка приёмки: `-C -` **перебивает мой `Range`** и просит у сервера
`bytes=<размер локального файла>-`. Для куска, который начинается не с нуля, это данные
**из другого места файла**: кусок получает верное начало и мусор дальше. По размеру
выглядит готовым, `ffprobe` длительность показывает верную, а декодер спотыкается
`Invalid NAL unit size` — или файл разваливается уже посреди нарезки.

**Как надо:** только явный диапазон и дописывание в конец, никакого `-C -`:
```bash
have=$(stat -f%z "$f" 2>/dev/null || echo 0)
curl -sL --noproxy '*' -r $((s+have))-$((s+want-1)) "$u" >> "$f"
```

**Конец `Range` сервер тоже игнорирует — обрывать запись самому.** Проверено на
Яндекс.Диске: после редиректа он уважает начало диапазона, а конец нет — льёт
до конца файла.
Куски выходят раздутыми (в одном эпизоде — все 28 кусков, +41% трафика в мусор), а счётчик
готовности `размер == want` не срабатывает никогда, и цикл кругов уходит в бесконечность.
Лечится одной трубой:
```bash
curl -sL --noproxy '*' -r $((s+have))-$((s+want-1)) "$u" | head -c $((want-have)) >> "$f"
```
`head -c` закрывает трубу на нужном байте, curl получает SIGPIPE и рвёт соединение.


**Проверять кусок пробой в НЕСКОЛЬКИХ точках, а не только по хвосту.** Кусок, который
докачивали в два-три подхода, бывает битым в СЕРЕДИНЕ, а хвост совпадает: одной хвостовой
пробы мало, я на этом пропустил брак и собрал нечитаемый файл. Рабочая проверка — 10 проб
по 64 КБ равномерно по куску против настоящих байт (54 МБ трафика на 85 кусков).
Проверку писать разово под конкретный диск: 10 проб по 64 КБ равномерно по куску.

**Склейку делать ТОЛЬКО когда все куски прошли проверку**, и обязательно сверять
итоговый размер байт в байт. Если склеить раньше, `cat` молча пропустит недостающие
куски и соберёт файл не того размера — у меня вышло 17,9 ГБ вместо 17,0.

**Финальная приёмка — сплошной декод, а не `ffprobe`.** Прокси и есть этот декод:
`ffmpeg -i src.MP4 -vf scale=-2:360,fps=10 ... 2> decode.log`, потом грепнуть лог
на `error|invalid|corrupt`. Безобидные строки, которые НЕ брак: `edit list`,
`Missing key frame while searching for timestamp`, `infe version < 2`,
`Guessed Channel Layout`.

⚠️ **Долгую закачку запускать ТОЛЬКО штатным фоновым режимом харнесса, не через `nohup … &`
из обычного вызова Bash.** Когда породивший вызов завершается, процесс-группа получает
SIGTERM: загрузчик молча умер на 1,6 ГБ из 14,8, а в логе остались 28 строк
`Terminated: 15`. Куски с явным Range докачиваются с места, так что потеря — только время.

⚠️ **Не править скрипт, пока он выполняется.** Bash дочитывает файл по ходу исполнения,
и правка на лету рвёт разбор в произвольном месте: в логе появилось
`syntax error near unexpected token 'do'` на строке, которой я не касался. Порядок —
остановить экземпляр, править, запустить заново; куски с явным Range докачиваются с места.

⚠️ Не запускать несколько экземпляров загрузчика разом — и **замок обязан быть с PID**.
Простой `mkdir .lock` бесполезен: после убитого экземпляра остаётся мёртвый замок, руки
сами тянутся сделать `rmdir .lock` — и следующий запуск идёт поверх ещё живого прошлого.
Так однажды работали два загрузчика: пять кругов подряд одни и те же куски приходили
битыми, я успел заподозрить сервер (проверил — он честно отдаёт `206` с верным
`Content-Range`, 6 из 6), а правда нашлась в `ps`: **два `curl` с ОДИНАКОВЫМ `-r`
от разных родителей**, пишущие `>>` в один файл. Отсюда битое ровно в СЕРЕДИНЕ куска.

**Диагностика в одну команду** — прежде чем винить сеть:
`ps -o pid,ppid,command -p $(pgrep -f curl | tr '\n' ,)` → одинаковые диапазоны = два экземпляра.

```bash
if [ -f "$W/.lockpid" ] && kill -0 "$(cat "$W/.lockpid")" 2>/dev/null; then
  echo "уже работает"; exit 1; fi
echo $$ > "$W/.lockpid"; trap 'rm -f "$W/.lockpid"' EXIT
```
Мёртвый замок снимается сам, живой не даёт запустить второй. Куски, которые трогали
два процесса, лечатся только удалением и закачкой начисто.

## Облачные диски режут скорость на больших файлах

Замер на Яндекс.Диске: первые ~10 ГБ идут на **12 МБ/с**, дальше скорость падает
до **0,2–0,5 МБ/с** и не восстанавливается. 14-гигабайтный исходник после этого
качается 15 часов. У других дисков числа свои, поведение то же.

Что с этим делать:
- Качать **в порядке важности**, не по номерам: сначала те файлы, откуда нужны
  самые проблемные шоты.
- Соединение рвётся регулярно — качать кусками по 200 МБ с докачкой, в 24–40 потоков
  (см. ниже про `-C -`: он ломает докачку). И **`-L`**: диск отвечает редиректом 302,
  без `-L` curl молча кладёт 0 байт.
- **Больше 24 соединений смысла не имеет.** Замер на этом каталоге: 1 поток 0,8 МБ/с ·
  8 → 1,1 · 24 → 2,4 · 48 → 2,5. Потолок ~2,5 МБ/с, дальше упор в лимит ссылки.
  17 ГБ = около двух часов, и это нормально, а не «что-то сломалось».
- Если файл так и не скачался — резать по сети **с проверкой глазами каждого куска**:
  тайм-код по HTTP всё равно врёт, поэтому отбирать не по времени, а по тому,
  ЧТО реально вырезалось. Для монотонной стадии (холст белеет→золотеет) это работает:
  порядок восстанавливается по содержимому.
