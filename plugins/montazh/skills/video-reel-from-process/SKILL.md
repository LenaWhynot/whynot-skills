# Рилс из съёмки процесса

Отбраковка здесь **97-99,6%**: из 76 минут материала в дело идут 17 секунд.
Вся ценность в ОТБОРЕ, не в резке. Ниже — метод, выведенный из четырёх эталонов
и восьми кругов правок на живых заказах.

## Что в комплекте

```
bin/contact-sheet.sh   контактные листы по всему исходнику
bin/strip.sh           полоса кадров одного куска
bin/assemble.sh        сборка ролика по раскладке
bin/stab.py            стабилизация (нужна редко, см. раздел про тряску)
bin/analyze/feat.py    признаки по прокси → feat_<исходник>.npz
bin/analyze/best.py    кандидаты по устойчивости + активности
bin/analyze/best2.py   то же для ТЁМНОГО исходника
bin/analyze/active.py  окна, где рука реально работает
bin/analyze/pick_active.py  живость при ограничении на тряску
bin/analyze/gap.py     кандидат, максимально не похожий на уже выбранные
bin/analyze/dup.py     проверка раскладки на повторы состояния
bin/analyze/strips.py  полосы кадров пачкой
```

**Рабочая папка** (её путь — в `WORKDIR`, иначе текущая):

```
proxy/<исходник>.mp4     прокси 360p, 10 fps — по нему считается и смотрится всё
feat_<исходник>.npz      признаки этого исходника
cut.json                 раскладка ролика: src · ss · d · zoom · kind
```

⚠️ **Python-скриптам нужен numpy**, он не входит в мастер настройки:
`python3 -m pip install --user numpy`. Проверить: `python3 -c "import numpy"`.
ffmpeg скрипты ищут сами — в `PATH`, затем в `~/.whynot-bin`, куда его кладёт
мастер первого запуска.

## Порядок работы

Ниже `$S` — папка навыка, чтобы строки не разъезжались:

```bash
S="${CLAUDE_PLUGIN_ROOT}/skills/video-reel-from-process"
command -v ffmpeg >/dev/null || bash "${CLAUDE_PLUGIN_ROOT}/skills/first-run-setup/bin/setup-ffmpeg.sh"
python3 -c "import numpy" 2>/dev/null || python3 -m pip install --user numpy
```

**1. Прокси на каждый исходник — один раз, дальше работаем только по нему.**

```bash
mkdir -p proxy
ffmpeg -nostdin -v error -i ИСХОДНИК.MP4 -vf "scale=-2:360,fps=10" -y proxy/A001.mp4
python3 "$S/bin/analyze/feat.py" proxy/A001.mp4 feat_A001.npz
```

**2. Посмотреть весь исходник глазами** — контактные листы по 24 кадра с подписью времени:

```bash
bash "$S/bin/contact-sheet.sh" proxy/A001.mp4 листы 72
```

**3. Кандидаты в шоты** — машина сужает, дальше решают глаза:

```bash
python3 "$S/bin/analyze/best.py"        feat_A001.npz 2 300 1.5 6   # устойчивые + живые
python3 "$S/bin/analyze/pick_active.py" feat_A001.npz 2 300 1.5 6   # живость при лимите на тряску
python3 "$S/bin/analyze/active.py"      A001 2 300 1.5 5            # где рука реально работает
python3 "$S/bin/analyze/gap.py"         A001 2 300 1.5 44.5 73.6    # непохожий на уже выбранные
```

**4. Каждого кандидата проверить ПОЛОСОЙ кадров**, а не одним кадром:

```bash
bash  "$S/bin/strip.sh" proxy/A001.mp4 44.5 1.5 полосы/01.png
python3 "$S/bin/analyze/strips.py" proxy/A001.mp4 "$PWD/полосы/all.png" 1.5 44.5 73.6 128.0
```

**5. Раскладка** — `cut.json` в рабочей папке; поля описаны в
[`reference/cut-format.md`](reference/cut-format.md), готовый образец — `reference/cut-format.json`.
Перед сборкой прогнать проверку на повторы состояния:

```bash
python3 "$S/bin/analyze/dup.py"
```

**6. Сборка и приёмка.** Собрать, затем снова посмотреть полосами — уже готовый ролик:

```bash
bash "$S/bin/assemble.sh" ИСХОДНИК.MP4 раскладка.txt рилс.mp4
bash "$S/bin/strip.sh" рилс.mp4 0 30 проверка.png
```

Дальше — метод: что считать, где ловушки и как собирать ритм.

## Правило номер один: СМОТРИ НА КАДРЫ

**Не выбирай моменты по числовым признакам вслепую.** Отпечаток 24×24 — это 576 точек,
на них не видно ни карандаша, ни руки, ни красиво ли. Пять версий подряд, собранных
слепым алгоритмом, заказчик забраковал; шестая, где кадры были ОТСМОТРЕНЫ, попала.

Порядок всегда двухслойный:

1. **Статистика сужает.** Сплошной проход ffmpeg по всем кадрам → отбраковка тряски,
   пауз, руки поверх работы → остаётся 40–60 кандидатов.
2. **Глаза выбирают.** Собрать контактные листы 6×4 с подписью времени, посмотреть их,
   выбрать финальные 18 с пониманием сюжета.

⚠️ **Кандидата смотреть ПОЛОСОЙ кадров, а не одним кадром.** Один кадр из середины
окна не показывает того, что происходит ВНУТРИ куска. На одном из заказов я отсмотрел все 19 шотов
по одному кадру, счёл их чистыми и отдал — заказчик вернул: «то ребёнок скачет, то ещё какая-то
хрень». Полоса по 6 кадров на шот нашла за минуту: в одном шоте через дверной проём сзади
проходит человек, в двух других поперёк кадра проносится смазом рука и куртка. В середине
всех трёх кусков кадр был идеальный.

```bash
# полоса на шот: 6 кадров по всей длительности d
ffmpeg -nostdin -ss $a -t $d -i reel.mp4 -vf \
 "fps=$(echo "6/$d"|bc -l),scale=125:222,drawtext=text='$i':fontcolor=yellow:fontsize=17\
  :box=1:boxcolor=black@0.9:x=2:y=2,tile=6x1:padding=2" -frames:v 1 -y strip_$i.png
```

Полосы сложить вертикально по 6-7 шотов на лист — весь ролик проверяется тремя картинками.
**Делать это ДО титров**, на сыром concat: переделывать дешевле, чем перерендеривать.

⚠️ **Финальный отбор смотреть кадром НЕ УЖЕ 240 px.** На большом холсте я выбрал два шота
по плиткам 150 px — на них затылок художника читался как «плечо, контекст». В готовом
ролике это оказалась голова во весь кадр, работы не видно. Контактный лист 6×4 годится,
чтобы СУЗИТЬ; финальные 10-15 кандидатов смотреть по 240-250 px в ряд по 6.

## Что считать по кадрам (сплошной проход, 24×24 RGB)

```
движение    = |кадр[t] − кадр[t−1]| по клеткам
тряска      = доля клеток, изменившихся выше 80-го перцентиля
              > 0.35 → едет КАМЕРА;  локальные изменения → работает РУКА
рука        = доля пикселей телесного цвета: R>95, G>40, B>20, R>G, R>B, R−G>15
прогресс    = |кадр[t] − кадр[t−5с]|
```

**Ключевое различение:** изменение пикселей — это в основном движение камеры,
а не работа. На реальном материале корреляция «время → близость холста к финалу»
оказалась **−0,07**, то есть нулевая, потому что камера ездит. Пока не отделишь
камеру от руки, алгоритм будет выбирать моменты, когда камера поехала.

## Пороги, проверенные на материале

| Признак | Порог | Что значит |
|---|---|---|
| тряска шота | **> 0,10** — не брать | забракованы шоты 0,126–0,357 |
| тряска для ЗУМА | **> 0,10** — зум запрещён | зум увеличивает дрожание |
| рука в кадре | > 40% телесного | «некрасивая рука», закрывает работу |
| яркость | вне 35–230 | чернота или пересвет |

## Четыре признака брака сверх «движения руки»

Движения руки мало. Оно находит момент, когда рука РАБОТАЕТ, и молчит про всё остальное:
смаз, людей в фоне, пустой холст, руку во весь экран. Каждый из этих признаков стоит
две строки numpy и снимает по классу брака. Пороги — **перцентили этого файла**, не числа.

| Признак | Как считать | Что режет | Порог |
|---|---|---|---|
| **резкость** | `|∂lum/∂x|.mean() + |∂lum/∂y|.mean()` | смазанную руку, проносящуюся поперёк кадра | ниже p45 — не брать |
| **фон** | движение в правой (или дальней) трети кадра | **людей, проходящих сзади** | выше p45 — не брать |
| **белое** | доля пикселей `sat<0.16 & lum>145` | пустой холст на пол-кадра | > 0.30 — не брать |
| **насыщенность** | `(max−min)/max` по кадру | «камера уехала на стену» | ниже p45 — не брать |

Считать на сетке **64×114**, не 24×24: на 576 точках нет ни резкости, ни фона.

Если стадия после фильтра даёт < 25 окон — **ослаблять пороги циклом** (шаг ~7 перцентилей,
коридор кожи ±0.02), а не отключать признаки. На одном из заказов «чёрный контур» прошёл только
с четвёртого ослабления, остальные девять стадий — с первого-второго.

⚠️ **Погоня за максимумом движения руки систематически выбирает кадры, где рука во весь
экран.** Это не баг метрики, а её смысл: больше всего «движения кожи» там, где кожи больше
всего. Поэтому коридор по коже (**0.18–0.42** на общем плане, 0.28–0.47 на макро) —
не украшение, а вторая половина метрики. Без него из десяти шотов семь будут «рука».

## «Трясётся» в начале — сначала выясни, ЧТО трясётся: камера или содержимое

Правка заказчика: «хорошо, но сделай в начале стабилизацию, чтобы не тряслось».
Инстинкт — стабилизировать открывашку. Замер показал обратное:

| шот | сдвиг кадра к кадру |
|---|---|
| открывашка | **0,77** — самый спокойный шот ролика |
| медиана тела | 2,42 |
| **таймлапс** | **10,73** |

Сдвиг КАМЕРЫ во всех шотах начала оказался ±1–6 px на 4К (0,1–0,3%) — штатив стоит
намертво, стабилизировать нечего. Трясётся содержимое таймлапса: при ×35,9 каждый
выходной кадр перепрыгивает 1,2 с исходника, рука между кадрами то есть, то нет.

**Что НЕ помогает** (проверено замером):
- стабилизация (привязка кадров к опорному, OpenCV): 10,73 → 10,67
- смаз движения `tmix=frames=16/32`: 10,73 → 9,63 / 9,47, при этом дорого
- `deshake` делает хуже, `vidstab` в сборке отсутствует

**Что помогает — сузить ОХВАТ таймлапса** (меньше исходных секунд на выходной кадр):

| охват | скорость | сдвиг |
|---|---|---|
| 80 с | ×35,9 | 10,73 |
| 65 с | ×29,1 | 10,28 |
| 55 с | ×24,7 | 8,52 |
| **40 с** | **×17,9** | **7,71** |

Ориентир — принятый эпизод: у 35-го таймлапс **8,46** при медиане ролика 2,16.
Значит прыгучий таймлапс для серии норма, но выше ~8,5 он читается как брак.

**Правило:** прежде чем чинить тряску, померить сдвиг ПОШТОТНО и отдельно оценить
смещение камеры. Если камера стоит, а сдвиг высокий — это содержимое, и лечится оно
не стабилизацией, а параметрами шота.

⚠️ **Стабилизатор на OpenCV лежит в комплекте — `bin/stab.py`** (привязка к опорному кадру,
оценка на серой копии 270×480, применение на нативном 4К, кроп полей). Он рабочий,
просто на этом материале не нужен: даёт запас 5–6% кропа за нулевой выигрыш.

## Таймлапс обязан КОНЧАТЬСЯ на действии, иначе читается как «оборвано»

Правка заказчика: «5 секунда не нравится, там оборвано». Замер тряски ничего не показал,
дефект нашёлся полосой кадров: последние **0,7 с таймлапса — мёртвый кадр**, рука ушла,
картинка замерла, и на этом стоп-кадре идёт жёсткая склейка. Движение обрывается раньше шота.

Причина: диапазон таймлапса упирался в паузу исходника. Плотный лист с шагом 2 с показал,
что в одном исходнике рука уходит из кадра с **46 по 64 секунду** — почти двадцать секунд статики,
и хвост таймлапса попал ровно в них.

⚠️ **Метрика «движение руки» этот случай не ловит**: работа тёплого цвета, маска кожи легла
на сам рисунок, и хвост 55–60 с показал «активность 4,43» при полном отсутствии руки в кадре.
Это та же грабля, что описана выше, но здесь она обманывает не при отборе шота, а при выборе
границ таймлапса.

**Правило:** прежде чем ставить диапазон таймлапса — построить плотный лист (шаг 2–3 с)
и глазами найти паузы. Конец диапазона ставить на кадре, где рука РАБОТАЕТ, а следующий шот
брать так, чтобы действие продолжалось (в одном эпизоде: таймлапс кончается оранжевым маркером
на 44,5 с, следующий шот — тот же оранжевый маркер на 73,6 с). Тогда склейка не видна.

**Побочная выгода:** короткий диапазон, упёртый в действие, ещё и спокойнее.
В том эпизоде 80 с → 40 с → 24,5 с дало сдвиг 10,73 → 7,42 → **7,01**.

**Если из-за укорочения таймлапса в истории появилась дыра — закрыть её обычным шотом**,
а не растягивать таймлапс обратно. В том эпизоде выпал участок 44–118 с (оранжевый воротник);
дыру закрыл обычный шот позже по времени, выбранным по максимуму расстояния состояния от концa таймлапса
(11,32 против 5,11 у более устойчивого, но похожего `@82.8`).

## Ритм снимать с ПРИНЯТОГО ролика, а не из головы

Когда ролик по этому сюжету уже принят, ритм не выдумывать и не брать из разбора эталона —
**замерить длительности его кусков** и применить дословно:

```bash
for f in out/parts/*.mp4; do ffprobe -v error -show_entries format=duration -of csv=p=0 "$f"; done
```

Детект склеек (`select=gt(scene,0.25)`) на таком материале **не работает** — все шоты
похожи (одна рука, один холст), сцен-детектор возвращает ноль склеек на 20 шотов.
Папка `parts/` — источник истины.

Так снятый с принятой «картины» ритм `2.20 · 1.30 1.20 1.30 1.30 1.10 2.23 1.40 1.30
1.50 1.50 1.60 1.70 1.60 1.70 1.80 1.10 1.30 · 3.80` (19 шотов, 30.93 с) лёг на новый
сюжет того же автора без единой правки.

## Оценивать ВЕСЬ КУСОК, а не кадр

Типичная ошибка: выбрать точку максимального изменения и играть от неё 1,5–2,9 с вслепую.
Внутри куска окажется пауза или тряска. **Считать признаки по всему окну длительностью d**
и отбрасывать окна, где чистое изменение ниже медианы (это статика, «долгая пауза»).

## Детектор эпизодов: слепой НЕ работает, проверено

Три подхода, все провалились на реальном материале:

| Подход | Что вышло |
|---|---|
| По позиции активной зоны | 14 обрывков по 10–30 с. **Камера переставляется**, одно место холста оказывается в разных координатах кадра |
| По цвету, который наносят | Почти везде «оранжевый» — это **рука**: кожа и есть оранжевый, а рука в кадре всегда |
| То же с исключением кожи | «Белый/серый/чёрный», хотя глазами видно карандаш → красный → белый → зелёный → чёрный. **24×24 слишком грубо**, сигнал тонет в окружающем холсте |

**Рабочая форма:** машина считает, зрение размечает.
Автоматика достаёт 40–60 кандидатов и строит контактные листы → модель СМОТРИТ и выдаёт
**карту стадий** (какая стадия, с какой по какую секунду, сколько шотов на неё, что пропустить)
→ внутри каждой стадии моменты снова выбирает автоматика по живости и порогам.

Карта стадий — обычный JSON: на каждую стадию имя, диапазон секунд, сколько шотов брать.
Она живёт в рабочей папке заказа и заводится заново на каждый сюжет.

## Метрика отбора: три неверных, одна верная

Самая дорогая ошибка этого класса задач. Метрика менялась трижды, и каждый раз правка заказчика
показывала, что предыдущая оптимизировала не то. Порядок ошибок повторяемый — не наступать заново.

| Метрика | Что берёт на самом деле | Вердикт заказчика |
|---|---|---|
| Среднее движение в кадре | моменты, где **ехала камера** | «трясётся, куски кривые» |
| Изменение картинки за кусок (начало→конец) | **скачки**: рука ушла — открылся готовый участок | «нет того, что он рисует, появляются итоги» |
| **Движение РУКИ** | руку, которая водит маркером | ✅ то, что нужно |

**Правильная метрика:** изменение пикселей **только в клетках с кожей**.
```python
sm = (R>95)&(G>40)&(B>20)&(R>G)&(R>B)&((R-G)>15)      # маска кожи
hand[1:] = (diff[1:] * sm[:-1]).sum(axis=(1,2)) / sm[:-1].sum(axis=(1,2))
```
Порог: **62-й перцентиль** по всему исходнику. Ниже — рука в кадре, но не работает.

⚠️ **И зеркальная ошибка: НЕ отбраковывать кадры за «много кожи».**
Я ставил потолок 40% и систематически выкидывал именно те кадры, где идёт работа.
Кожа должна быть **в коридоре 0.28–0.47**: меньше — руки нет, виден только результат;
больше — рука закрывает работу.

## Критерий шота — «картинка СТАЛА ДРУГОЙ», а не «рука активно работает»

Самая живучая ошибка отбора, вылезала три раза в одном ролике. Активная рука бывает и там,
где художник десятый раз обводит один и тот же контур: метрика горит, а на экране ничего
не происходит. заказчик этот класс брака чувствует сразу и формулирует как «затянуто» —
не «плохой кадр», а именно **«долго»**.

На одном из заказов так прошли три шота подряд — `74@272`, `74@291`, `74@323`: оранжевая голова
с двумя белыми глазницами. Между 272-й и 356-й секундой исходника рисунок **не менялся
вообще** (следующее событие — синий зрачок), а я отдал этому куску 4 секунды.
Каждый шот по отдельности проходил все пороги.

**Правило:** прежде чем ставить шот в раскладку, сравнить его с УЖЕ ВЫБРАННЫМ предыдущим.
Похожи — второй не нужен, каким бы хорошим он ни был по цифрам.

```python
# подпись состояния работы: кадр в момент t, огрублённый и без кожи
sig = lambda t: np.where(skin[t], np.nan, lum[t])          # рука вырезана
diff = np.nanmean(np.abs(sig(tb) - sig(ta)))               # насколько картинка изменилась
# diff ниже ~p35 по всем парам кандидатов → это ОДНО состояние, брать один шот
```

⚠️ **Границы стадий выводить из прогресса, а не размечать на глаз.** Я задал стадии
диапазонами по контактному листу — и «глаза» с «зрачком» разъехались на 85 секунд,
внутри которых не менялось ничего. Считать `|кадр[t] − кадр[t−30с]|` по всему исходнику:
всплески = моменты, когда работа реально меняется, они и есть границы. Стадия, внутри
которой прогресс плоский, получает **один шот**, сколько бы хороших кандидатов в ней ни было.

## Маркер в цвет поверхности — брак, который НЕ ловит ни одна метрика

Правка заказчика: «10 секунду удали, там где белым маркером рисует, а то ничего не видно».
Шот проходил всё: тряска 0,235, резкость 28,5, рука работает, картинка внутри шота меняется
**11,81 при медиане 6,26** — то есть по «изменению состояния» он был одним из ЛУЧШИХ в ролике.
Белый маркер по белому холсту двигает яркость не хуже чёрного, метрике всё равно, а глазу
нечитаемо.

**Правило:** после отбора посмотреть, каким цветом идёт штрих и по какой поверхности.
Совпали — выкинуть шот, сколько бы он ни набрал. Классика этого автора: белый по белому,
жёлтый по жёлтому, прозрачный лайнер по светлому. Проверяется одним контактным листом
из 4 кадров на шот в 250 px — на 125 px маркер не различить по цвету.

Отрицательный вывод усилен: метрика «картинка стала другой» отвечает на вопрос
«изменилось ли», а не «видно ли ЧТО изменилось».

## «Кожа» врёт на тёплом рисунке — глазами проверять НАЛИЧИЕ руки

Продолжение известной оговорки про детектор кожи, но в другом месте: не на общем плане,
а на макро, где метрике доверяешь больше всего. На одном из заказов я отранжировал поздний кусок
9676 по «движению руки» и получил уверенных лидеров — `@341.9` рука 13.1, `@397.6` рука 10.0
при медиане 2.3. **Руки там нет ни в одном кадре.** Рисунок сам оранжевый, маска кожи легла
на него, а «движение» дала едущая камера.

**Правило:** высокий балл руки — гипотеза, а не факт. Прежде чем ставить шот, посмотреть
полосу и убедиться, что рука ВИДНА. Особенно когда работа в тёплой гамме — оранжевый,
телесный, золотой, дерево.

## НЕ списывать отрезок исходника по нескольким пробам — сканировать плотно

Самая дорогая ошибка этой сессии, и она про метод, а не про кадры.
Я отранжировал хвост 9676 по «движению руки», посмотрел **четыре** окна — 341.9, 352.1,
375.4, 397.6 — не увидел руки ни в одном и объявил: «после 300-й секунды работы нет,
художник возится за кадром». Вырезал весь отрезок.

Заказчик: «на рисунке ещё финальные штрихи добавляются, самые интересные, и ты их вырезал».

Плотный лист по 9676 через каждые 2 с показал: **с 298 до 414 рука почти непрерывно кладёт
чёрный контур** — обводит глаза, рот, зубы, добавляет детали фона. Мои четыре пробы попали
ровно в паузы между штрихами. **Четыре точки на 110 секунд — это не проверка, это лотерея.**

**Правило:** прежде чем объявить отрезок пустым, построить **сплошной контактный лист
с шагом 2–3 с** по всему отрезку. Один `ffmpeg` на 40 секунд работы:

```bash
ffmpeg -nostdin -ss $A -t $((B-A)) -i proxy.mp4 -vf \
 "fps=0.5,scale=132:235,drawtext=text='%{eif\:$A+t\:d}':fontcolor=yellow:fontsize=17\
  :box=1:boxcolor=black@0.9:x=2:y=2,tile=9x7:padding=2" -frames:v 1 -y dense.png
```

Отрицательный вывод («тут нечего брать») требует БОЛЬШЕ доказательств, чем положительный,
а не меньше: положительный проверяется одним найденным шотом, отрицательный — только
сплошным просмотром.

## Конец каждого исходника досматривать до последнего кадра

Кадр готовой работы без руки почти всегда лежит **в самом хвосте файла**: художник кладёт
последний штрих и убирает руку, а камера ещё пишет.

На одном из заказов я дважды пропустил его, потому что обрывал разбор на 409-й секунде — там
ещё идёт штрих, и мне казалось, что дальше то же самое. В 9676 после **412-й** рука уходит
и остаётся 3,7 с чистого крупного плана законченной работы. Именно этот кадр заказчик просил
подержать, и его дважды не было в раскладке.

**Правило:** по каждому исходнику отдельно посмотреть последние 10–15 секунд покадрово.
Дёшево (один `ffmpeg`), а находка — тот самый шот, ради которого весь ролик снимали.

## Фиксация итога — на КРУПНОМ плане работы, не на общем плане

Заказчик: «финальный результат можно подержать секунды 1,5 и увеличивать, чтобы зафиксировать
итог». Я растянул и приблизил закрывашку — общую доску. Мимо: «не то, ты удлинил
не последний кадр, а получается предпоследний, где рисунок крупный и закончен».

**Раскладка концовки, принятая:**
```
последний штрих           1.3 с   рука доводит деталь
ГОТОВАЯ РАБОТА крупно     1.6 с   рука ушла, рисунок целиком, НАЕЗД 10%   ← фиксация итога
закрывашка, общий план    2.1 с   доска, рука показывает новую работу, CTA
```
Общий план в конце — это **контекст** («вот куда встала сегодняшняя работа»), а не итог.
Итог фиксируется там, где итог видно: на самой работе.

## Финальные штрихи — самое ценное в ролике, их нельзя резать

заказчик назвал их «самые интересные». Логика зрителя: весь ролик он смотрит, как из ничего
собирается работа, и последние касания маркера — это кульминация, момент «готово».
Вырезать их ради хронометража — всё равно что оборвать историю на предпоследней фразе.

**Держать в раскладке 2–4 шота последней стадии**, где рука реально доводит детали,
и ставить их прямо перед закрывашкой. На одном из заказов это `76@379.5` · `403.5` · `409.0` —
контур, штрихи внизу, последний штрих сверху; каждый показывает свой участок работы.

⚠️ Не путать с «долгим кадром на незавершённой работе»: держать долго нельзя **статичный**
кадр недоделки. Активные финальные штрихи — наоборот, обязательны.

## Одно замечание заказчика = прогнать ВЕСЬ ролик на этот дефект

заказчик называет **секунды, а не класс ошибки**: «затянуто начало», «22–23 долго»,
«11–13 долго». Это были три проявления ОДНОГО дефекта — соседние шоты с одинаковой
картинкой. Я чинил по одной названной точке и получил три круга правок вместо одного.

**Услышал замечание — найди его причину и просей по ней весь ролик**, включая места,
на которые заказчик не жаловался. Дешевле один пересбор, чем три.

Тот же приём работает и на «некрасивых» кадрах: нашёл человека в фоне в одном шоте —
прогони фон-метрику по всем восемнадцати, а не только по соседним.

## Шоты одной стадии брать КУЧНО

Разброс шотов одной стадии по всему её диапазону читается как слайдшоу результатов —
заказчик сказал «ломано». Внутри стадии искать **окно, где подряд помещаются все её шоты**
с промежутками 4–6 с. Тогда соседние кадры показывают одно продолжающееся действие.

Пример: зелёная заливка была 721 · 778 (вразброс на 150 с) → стало 578 · 583 · 589.

## Проверять, что в диапазоне стадии реально работают

Диапазон стадии ≠ работа идёт непрерывно. Внутри бывают мёртвые паузы.
Шот «сердечки» стоял на 1124 с, где движение руки **0.15** — формально внутри стадии,
фактически пауза. Сердечек в ролике не было видно вообще.
**Всегда проверять движение руки в КОНКРЕТНОМ выбранном окне, а не только в стадии.**

## Куда девать вес хронометража

Дефолт — **на финал**. Заказчик: «на начало много фокуса, сместить на конец».
Рабочая раскладка на 35 с: первая треть ~10 с, последняя ~16 с.
Стадиям финала (детали, украшения фона, готовая работа) давать **больше шотов и длиннее**:
2.0 → 2.2 → 2.4 с с нарастанием.

## Шрифт титров

**Poppins ExtraBold** — совпал с эталоном (проверено против Arial Rounded, Impact,
Arial Black, Futura, Avenir, Helvetica — не подходят).
Ставится: `curl -L https://github.com/google/fonts/raw/main/ofl/poppins/Poppins-ExtraBold.ttf -o ~/Library/Fonts/Poppins-ExtraBold.ttf`

Текст **целиком белый** с чёрной обводкой `borderw=8`. Никаких двухцветных слов —
это была моя ошибка от разглядывания мелкого кропа.

## Серию закреплять рецептом, а не собирать каждый раз заново

Как только по автору принят первый ролик, его раскладка перестаёт быть догадкой.
Дальше она — рецепт, и второй эпизод собирается по нему, а не с нуля.

Рецепт держать рядом с заказом, отдельным файлом. В нём:

- **длительности шотов** принятого ролика, снятые с `parts/` (см. раздел про ритм);
- **брендинг**: титры или их отсутствие, вид концовки, водяной знак, целевая длина;
- **особенности камеры автора**: `rotation`, кодек, объём эпизода, имена файлов;
- **рамка кропа** на каждый исходник, если съёмка горизонтальная;
- **что уже браковали** — чтобы не предлагать это снова.

Порядок на новом эпизоде: прокси → признаки → кандидаты → контактные листы →
`cut.json` по рецепту → сборка → полосы кадров на проверку. Формат раскладки — [`reference/cut-format.md`](reference/cut-format.md).

⚠️ **Меняется камера — рецепт устаревает молча.** Смена аппарата у автора меняет
кодек, `rotation` и объём файлов; раскладка при этом выглядит рабочей, а выходит боком
(в буквальном смысле — см. раздел про `rotation`). Первым делом на новом эпизоде
сверять метаданные с тем, что записано в рецепте.

## ГЛАВНОЕ: у каждого автора СВОЙ шаблон, не один общий

Самая дорогая ошибка второго уровня. Я разобрал четыре ролика как один жанр, вывел общие
правила — и перенёс брендинг одного автора на материал другого. Заказчик: «тут эталон именно
для этого видео, оно там иначе смонтировано».

| | Автор А: рисунок, макро руки | Автор Б: большой холст, общий план |
|---|---|---|
| Титры | название серии + счётчик эпизода | **нет вообще** |
| Финал | вопрос-CTA печатается по буквам | **затемнение + иконка сети и ник** |
| Планы | почти всё макро руки | 2 широких, дальше средние с рукой |
| Таймлапс | есть, ×52,8 | **нет** |
| Водяной знак | нет | **ник в углу весь ролик** |
| Длительность | 34,6 с | 12,5–13,6 с |

**Шаблон состоит из ДВУХ слоёв, и их нельзя смешивать:**

**Слой монтажа — общий, переносится.** Только жёсткие склейки · хронологический порядок ·
рука в кадре работает · шоты стадии кучно в 3–15 с · отбраковка 97–99% ·
брать из той части стадии, где предмет читается · вес хронометража на финал.

**Слой брендинга — свой у каждого, ИЗВЛЕКАТЬ ИЗ ЭТАЛОНОВ ПОЛЬЗОВАТЕЛЯ.**
Титры или их отсутствие · тип концовки · водяной знак · целевая длительность ·
наличие таймлапса. **Никогда не подставлять дефолт от другого автора.**

**Порядок работы:** прежде чем резать — открыть эталоны ЭТОГО автора и посмотреть
на кадры. Не тайминги, а именно кадры: есть ли текст, какая концовка, какие планы.

## Пороги — только перцентили ЭТОГО материала

Абсолютные числа, настроенные на одном сюжете, на другом отсекают почти всё.

| | Автор А (макро руки) | Автор Б (общий план) |
|---|---|---|
| Кожа в кадре, медиана | 0,359 | **0,103** |
| Прошло бы по порогу 0,28–0,47 | — | **19% кадров** |

Считать пороги **от распределения конкретного файла**: тряска ниже 55–60-го перцентиля,
активность выше 55–60-го. Числа выйдут разные (0,099 и 0,21 для одного файла, 0,142 и 0,47
для другого) — правило одно.

⚠️ **Абсолютный порог яркости выкашивает целый сюжет.** Порог «вне 35–230 — брак»
у автора Б отбраковал почти весь главный исходник: тёмная студия с розовым светом
даёт яркость **29–39 на всех 553 секундах**. Эталонный ролик этого автора снят ровно в этой
темноте и выглядит нормально. Яркость — такой же перцентиль, как тряска и движение.

⚠️ **Детектор кожи ненадёжен как основная метрика.** Он ловит всё тёплое: золотую краску,
дерево, оранжевые пятна. У автора Б он показывал «кожу» 0,37–0,41 там, где человека
в кадре нет вообще. Использовать только там, где заведомо крупный план рук;
иначе брать общую активность кадра.

## Каркас ролика

```
открывашка   3.0 с   общий план · титул с счётчиком серии
тело        ~30 с    18 шотов, медиана 1.5–1.7 с, ТОЛЬКО жёсткие склейки
таймлапс     1.5–2.2 с  ×30–55, один на ролик, НА ПЕРЕХОДЕ МЕЖДУ СТАДИЯМИ
закрывашка   3.8 с   общий план · CTA-типографика печатается по буквам
```

**Длительность обрамления по четырём эталонам:**

| Ролик | Первый шот | Последний |
|---|---|---|
| Автор А, рисунок | 1,90 | 1,90 |
| Автор Б, дубль 1 | **3,80** | **4,00** |
| Автор Б, дубль 2 | 1,00 | **4,03** |
| Автор В, скульптура | 0,73 | 1,97 |

У автора А открывашка держится титулом, поэтому там хватает 1,9. Без плотного титула
брать **3,0 на вход и 3,8 на выход** — финал это показ результата, ему нужно время.
заказчик забраковал 1,9/1,9 как «короткий».

**Ритм эталона, брать дословно** (сумма 34,55 с):
`1.90 1.67 2.53 1.73 1.40 0.90 1.47 2.23 1.83 1.07 1.63 1.23 1.47 1.73 2.03 2.87 2.00 1.33 1.63 1.90`

Заход медленнее → середина мельче (минимум 0,90) → шестнадцатый шот самый длинный (2,87)
→ финал тормозит. Случайные длительности вокруг медианы дают плоский ритм и заказчик это видит:
у эталона разброс 0,90–2,87 и σ=0,47, у плоской версии σ=0,29.

## Жёсткие правила сборки

- **Хронология строго вперёд.** Показал почти готовое, потом вернулся к началу — брак.
  Таймлапс охватывает 70 секунд исходника: **следующий шот должен начинаться после конца
  его диапазона**, иначе повтор уже показанного.
- **Позиция таймлапса в ролике = его позиция в исходнике.** Не ставить по индексу.
- **Только жёсткие склейки.** 39 из 39 в четырёх эталонах. Никаких переходов.
- **Сюжет по этапам.** Материал читается по цветам: карандаш → красный → белый → зелёный →
  чёрный контур. Один шот на этап, по порядку. Двадцать шотов про двадцать разных мест —
  бессвязно, заказчик скажет «рваные куски».
- **Общий план в середине** как воздух между макро.
- **Проезд камеры не «акцент», а брак.** Не вставлять специально.

## ПЕРВЫМ ДЕЛОМ: проверить `rotation` — иначе весь разбор идёт боком

Профессиональные камеры пишут вертикаль как **3840×2160 плюс `rotation=90` в метаданных**.
`ffprobe -show_entries stream=width,height` покажет ЛЕЖАЧИЙ кадр и соврёт.
Правда — в side_data:

```bash
ffprobe -v error -select_streams v:0 -show_entries stream_side_data=rotation -of csv=p=0 ФАЙЛ
# 90  → настоящий кадр 2160x3840, это УЖЕ ровно 9:16, кадрировать нечего
```

У автора Б все восемь исходников оказались `rotation=90`. Я полдня разбирал
**положенный на бок мир**: считал холст «горизонтальным», изобретал сдвиги кропа,
браковал шоты за «голова закрывает работу» — а в истинной ориентации это художник,
стоящий у вертикального холста, ровно как в эталонах автора.

**Ловушка вдвойне подлая:** ffmpeg разворачивает кадр САМ при чтении локального файла,
но при чтении того же файла **по HTTP side_data может не доехать** — и тот же фильтр
даёт разный результат. Прокси, снятый по сети, был лежачий; локальный 4K — стоячий;
одинаковый `crop` вырезал из них разные куски. Именно на этом я потерял два прогона.

**Порядок:**
1. Проверить `rotation` у КАЖДОГО исходника до любого анализа.
2. Прокси снимать с ЛОКАЛЬНОГО файла, а не по ссылке.
3. Если `rotation=90` и кадр 2160×3840 — фильтр целиком: `scale=1080:1920`. Без кропа.
4. Если читать всё-таки приходится по ссылке — **поворачивать руками**: `transpose=1`
   перед `scale`. Проверено на этом материале: локально ffmpeg крутит сам, по HTTP нет.

## Кадрирование 16:9 → 9:16 — своё на КАЖДЫЙ исходник

> Всё ниже — только если исходник ДЕЙСТВИТЕЛЬНО горизонтальный. Сначала проверь `rotation`
> по разделу выше: у вертикальной съёмки кадрировать нечего.

Съёмка горизонтальная, вывод вертикальный: `crop=1080:1920` из отмасштабированного кадра
берёт **лишь 32% ширины** (1215 px из 3840). Это не технический шаг, а решение о композиции,
и оно разное у разных исходников одного и того же сюжета.

Две рамки, обе нужны:

```bash
# ШИРОКИЙ план — полная высота, X целится на ПРЕДМЕТ, а не в центр
scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920:<X>:0
# СРЕДНИЙ/крупный — резать ВНУТРЬ предмета из нативного 4K, апскейл 1.13x
crop=956:1700:<X>:<Y>,scale=1080:1920:flags=lanczos
```

- **Центр по умолчанию — почти всегда мимо.** У автора Б предмет стоял слева,
  художник справа. Центральный кроп (X=1166) показывал затылок и обрезал холст;
  правильный X оказался **160**. Разница видна сразу, ищется перебором 3-4 значений.
- **У среднего плана полная высота даёт треть кадра чёрного потолка.** Лечится только
  кропом внутрь предмета: вертикального запаса нет (2160 → 1920 это 240 px), а
  горизонтального — 2333 px.
- Проверять рамку **на нескольких моментах**: если камеру не двигали, один X держится
  на весь файл (проверено на 553 с).
- Смотреть рамку на прокси: координаты прокси 640×360 умножаются на 6 → координаты 4K.

## Зум — пятая константа, её легко пропустить

В эталоне есть **плавные наезды и отъезды внутри шотов**. Исходник 4K, вывод 1080p —
запас вчетверо, зум цифровой и без потери качества.

```bash
# ЗУМ НА НАТИВНОМ 4K, уменьшение ОДИН раз в конце
scale=2160:3840:force_original_aspect_ratio=increase,crop=2160:3840,fps=30,
zoompan=z='1+0.13*on/<кадров>':d=1:x='iw/2-(iw/zoom/2)':y='ih/2-(ih/zoom/2)':s=2160x3840:fps=30,
scale=1080:1920:flags=lanczos
```

- **Зумить только устойчивые шоты** (тряска < 0,10). Иначе усиливается дрожание.
- **Никогда не зумить открывашку и закрывашку** — там общий план, обрезка съедает край кадра.
- Величина 10–14%. Наезд подчёркивает деталь, отъезд показывает контекст.
- Зум ПОСЛЕ уменьшения до 1080p даёт дрожание (округление до пикселя) и мыло. Только 4K.

## Перемотка по HTTP ВРЁТ — резать только с локального файла

Самая дорогая ошибка этой сессии: весь отбор шотов оказался недействительным, потому что
`ffmpeg -ss <t> -i <http-url>` попадает **не туда**. На 4,7 ГБ VBR-файле кадр по одному
и тому же тайм-коду из сети и из локального прокси — **разные моменты**, расхождение
десятки секунд. Индекс (moov) лежит в конце файла, по сети ffmpeg его толком не читает
и оценивает позицию по битрейту.

Контрольный опыт, который это установил: на ЛОКАЛЬНОМ файле прокси и 4K по одному
тайм-коду совпадают кадр в кадр. Значит врёт не прокси-конвейер, а сетевая перемотка.

**Правило: анализировать можно по сети, РЕЗАТЬ — только с файла на диске.**
Прежний вывод «byte-range на 0,4–2,7%, ничего не храним» держится только для СБОРА
признаков сплошным чтением. Для извлечения кусков файл надо скачать — кусками
с явным `Range` (НЕ `-C -`, см. ниже), с многоточечной проверкой и сплошным декодом.

Если скачать нельзя — единственный честный вариант, `-ss` ПОСЛЕ `-i` (точная перемотка
декодированием с начала), но это тянет весь файл ради одного куска.

⚠️ Признак беды в логе: `Unexpected offset: expected …, got 0` и `partial file`.
Появились — значит поток рвался, тайм-коды под подозрением.

## ⚠️ `curl -C -` ВМЕСТЕ с `-r` тихо портит файл — так качать нельзя

Самая дорогая ошибка приёмки: `-C -` **перебивает мой `Range`** и просит у сервера
`bytes=<размер локального файла>-`. Для куска, который начинается не с нуля, это данные
**из другого места файла**: кусок получает верное начало и мусор дальше. По размеру
выглядит готовым, `ffprobe` длительность показывает верную, а декодер спотыкается
`Invalid NAL unit size` — или файл разваливается уже посреди нарезки.

**Как надо:** только явный диапазон и дописывание в конец, никакого `-C -`:
```bash
have=$(stat -f%z "$f" 2>/dev/null || echo 0)
curl -sL --noproxy '*' -r $((s+have))-$((s+want-1)) "$u" >> "$f"
```

**Конец `Range` сервер тоже игнорирует — обрывать запись самому.** Проверено на
Яндекс.Диске: после редиректа он уважает начало диапазона, а конец нет — льёт
до конца файла.
Куски выходят раздутыми (в одном эпизоде — все 28 кусков, +41% трафика в мусор), а счётчик
готовности `размер == want` не срабатывает никогда, и цикл кругов уходит в бесконечность.
Лечится одной трубой:
```bash
curl -sL --noproxy '*' -r $((s+have))-$((s+want-1)) "$u" | head -c $((want-have)) >> "$f"
```
`head -c` закрывает трубу на нужном байте, curl получает SIGPIPE и рвёт соединение.


**Проверять кусок пробой в НЕСКОЛЬКИХ точках, а не только по хвосту.** Кусок, который
докачивали в два-три подхода, бывает битым в СЕРЕДИНЕ, а хвост совпадает: одной хвостовой
пробы мало, я на этом пропустил брак и собрал нечитаемый файл. Рабочая проверка — 10 проб
по 64 КБ равномерно по куску против настоящих байт (54 МБ трафика на 85 кусков).
Проверку писать разово под конкретный диск: 10 проб по 64 КБ равномерно по куску.

**Склейку делать ТОЛЬКО когда все куски прошли проверку**, и обязательно сверять
итоговый размер байт в байт. Если склеить раньше, `cat` молча пропустит недостающие
куски и соберёт файл не того размера — у меня вышло 17,9 ГБ вместо 17,0.

**Финальная приёмка — сплошной декод, а не `ffprobe`.** Прокси и есть этот декод:
`ffmpeg -i src.MP4 -vf scale=-2:360,fps=10 ... 2> decode.log`, потом грепнуть лог
на `error|invalid|corrupt`. Безобидные строки, которые НЕ брак: `edit list`,
`Missing key frame while searching for timestamp`, `infe version < 2`,
`Guessed Channel Layout`.

⚠️ **Долгую закачку запускать ТОЛЬКО штатным фоновым режимом харнесса, не через `nohup … &`
из обычного вызова Bash.** Когда породивший вызов завершается, процесс-группа получает
SIGTERM: загрузчик молча умер на 1,6 ГБ из 14,8, а в логе остались 28 строк
`Terminated: 15`. Куски с явным Range докачиваются с места, так что потеря — только время.

⚠️ **Не править скрипт, пока он выполняется.** Bash дочитывает файл по ходу исполнения,
и правка на лету рвёт разбор в произвольном месте: в логе появилось
`syntax error near unexpected token 'do'` на строке, которой я не касался. Порядок —
остановить экземпляр, править, запустить заново; куски с явным Range докачиваются с места.

⚠️ Не запускать несколько экземпляров загрузчика разом — и **замок обязан быть с PID**.
Простой `mkdir .lock` бесполезен: после убитого экземпляра остаётся мёртвый замок, руки
сами тянутся сделать `rmdir .lock` — и следующий запуск идёт поверх ещё живого прошлого.
Так однажды работали два загрузчика: пять кругов подряд одни и те же куски приходили
битыми, я успел заподозрить сервер (проверил — он честно отдаёт `206` с верным
`Content-Range`, 6 из 6), а правда нашлась в `ps`: **два `curl` с ОДИНАКОВЫМ `-r`
от разных родителей**, пишущие `>>` в один файл. Отсюда битое ровно в СЕРЕДИНЕ куска.

**Диагностика в одну команду** — прежде чем винить сеть:
`ps -o pid,ppid,command -p $(pgrep -f curl | tr '\n' ,)` → одинаковые диапазоны = два экземпляра.

```bash
if [ -f "$W/.lockpid" ] && kill -0 "$(cat "$W/.lockpid")" 2>/dev/null; then
  echo "уже работает"; exit 1; fi
echo $$ > "$W/.lockpid"; trap 'rm -f "$W/.lockpid"' EXIT
```
Мёртвый замок снимается сам, живой не даёт запустить второй. Куски, которые трогали
два процесса, лечатся только удалением и закачкой начисто.

## Оценивать окно ЦЕЛИКОМ — включая то, что въезжает в кадр

Раздел «оценивать весь кусок» выше — про паузы. Есть вторая половина той же ошибки:
**перекрытие приходит не сразу.** Я выбрал три шота по первому кадру — рука с маркером,
холст читается. В готовом ролике через полсекунды в кадр въезжала голова художника
и занимала половину экрана все оставшиеся 1,5–2,4 с.

Проверять кандидата **киноплёнкой из 5 кадров по всей длительности окна**, не одним кадром:
```bash
ffmpeg -ss <t> -t <d> -i прокси.mp4 -vf "crop=<рамка>,scale=145:258,fps=2.8,tile=5x1" -frames:v 1 полоска.png
```
Дёшево (прокси локальный), и ловит ровно тот брак, который иначе виден только в финале.

## Облачные диски режут скорость на больших файлах

Замер на Яндекс.Диске: первые ~10 ГБ идут на **12 МБ/с**, дальше скорость падает
до **0,2–0,5 МБ/с** и не восстанавливается. 14-гигабайтный исходник после этого
качается 15 часов. У других дисков числа свои, поведение то же.

Что с этим делать:
- Качать **в порядке важности**, не по номерам: сначала те файлы, откуда нужны
  самые проблемные шоты.
- Соединение рвётся регулярно — качать кусками по 200 МБ с докачкой, в 24–40 потоков
  (см. ниже про `-C -`: он ломает докачку). И **`-L`**: диск отвечает редиректом 302,
  без `-L` curl молча кладёт 0 байт.
- **Больше 24 соединений смысла не имеет.** Замер на этом каталоге: 1 поток 0,8 МБ/с ·
  8 → 1,1 · 24 → 2,4 · 48 → 2,5. Потолок ~2,5 МБ/с, дальше упор в лимит ссылки.
  17 ГБ = около двух часов, и это нормально, а не «что-то сломалось».
- Если файл так и не скачался — резать по сети **с проверкой глазами каждого куска**:
  тайм-код по HTTP всё равно врёт, поэтому отбирать не по времени, а по тому,
  ЧТО реально вырезалось. Для монотонной стадии (холст белеет→золотеет) это работает:
  порядок восстанавливается по содержимому.

## Стоимость: отбор дешевле починки

`deshake` на 4K — **больше двух минут на кусок в 2 секунды**, непригодно.
На 1620 с rx=16 — 11 секунд. Зум на 4K без стабилизации — 2 секунды.

**Вывод: не чинить дрожащий кусок, а не брать его.** Отбраковка стоит доли секунды.

## Титры

Плашка на открывашке с нулевого кадра, без анимации, уходит со склейкой.
Финальный CTA **печатается по буквам** за ~0,4 с, вторая половина другим цветом.
Субтитров в таких роликах НЕТ — речи нет вообще, дорожка пустая.

### Границу «футаж / типографика» не размывать

**ffmpeg владеет футажом.** Всё, что ниже, он делает дешевле и предсказуемее любого
рендера, и именно так собраны принятые эталоны:

| Задача | Чем | Почему |
|---|---|---|
| склейки футажа | `ffmpeg concat`, встык | 39 из 39 в эталонах, правило не трогаем |
| зум и наезды | `ffmpeg zoompan` на нативном 4K | 2 с на кусок, без апскейла |
| затемнение финала | `ffmpeg fade=t=out` | это не переход, а концовка |
| титры и CTA | `ffmpeg drawtext` + `-filter_complex_script` | то, чем собраны принятые ролики |
| motion blur | не вводим | дорого, и в эталонах его нет |
| музыка | не кладём, `-an` | в эталонах дорожка пустая, звук ставят в приложении сети |

Субтитров в таких роликах нет по определению — речи нет, дорожка пустая.

⚠️ Если для сложной кинетической типографики берётся отдельный рендер (например
Remotion-проект), он входит в конвейер **только оверлеем с альфой** — прозрачный
ProRes 4444, дальше `overlay` поверх готового футажа. Исходники в такой проект
не копируются никогда, иначе на каждый ролик уезжают гигабайты.

## Грабли ffmpeg

- В цикле `while read` обязательно **`ffmpeg -nostdin`**, иначе съест список файлов.
- **`bash` в macOS — 3.2, `declare -A` не работает.** Ассоциативные массивы молча падают;
  писать через функцию-диспетчер `case`, а не через словарь.
- **Ссылки на файлы в облачных дисках протухают между вызовами.** Брать свежий `href` на КАЖДЫЙ шот
  и после каждого куска проверять `ffprobe`, что длительность совпала; иначе получаются
  файлы по 48 байт, и `concat` их молча проглатывает.
- **Стрим 4K по HTTP виснет намертво без `-reconnect`.** Признак: CPU крутится, счётчик
  байт стоит. Лечится `-reconnect 1 -reconnect_delay_max 30 -rw_timeout 20000000
  -multiple_requests 1`. НЕ добавлять `-reconnect_streamed` к seekable-источнику —
  оно ломает докачку по Range. `-hwaccel videotoolbox` даёт ×1,7 на декоде 4K.
- **Один сплошной проход → прокси 640×360, и дальше всё локально.** 705 с исходника
  превращаются в 6,7 МБ, по которым можно смотреть кадры и мерить сколько угодно
  бесплатно. Иначе каждый взгляд на кадр — новый сетевой запрос.
- Перед сборкой **чистить `list.txt`** — остатки от прошлого прогона дают лишние секунды.
- Исходники с телефона и камеры идут с `rotation=90`, ffmpeg поворачивает сам.
- В одном проекте бывают смешаны 1080p и 4K, 60 и 24 fps — нормализовать перед склейкой.

## Устойчивость и живость выбирать ВМЕСТЕ — иначе чинишь тряску и получаешь «тупые паузы»

Ошибка второго круга правок на другом эпизоде, и она обидная: заказчик пожаловался на тряску,
я отранжировал окна по устойчивости — и **шот из живого стал мёртвым**.

| | тряска | мёртвых кадров |
|---|---|---|
| было `@813.0` | 0,356 | — |
| «починил» `@811.1` | **0,190** ✅ | **92%** ❌ |

Заказчик: «тело было на предыдущих лучше, сейчас много тупых пауз». Причина простая и
повторяемая: **окно без движения камеры — это часто окно, где не движется и рука.**
Оптимизируя одну метрику, систематически проваливаешь вторую.

**Правило: отбирать по живости при ОГРАНИЧЕНИИ на тряску, а не наоборот.**
Сортировать по `hand.mean()`, отбрасывая всё, где `shake.max() > p80`. Готовый отборщик —
`bin/analyze/pick_active.py`.

⚠️ **«Мёртвость» считать по СТАДИИ, а не по всему файлу.** Во второй половине съёмки
камера ближе, движения мельче — глобальный `p40` движения руки красит всю позднюю часть
в «мёртвую» и отборщик возвращает пусто. Там с глобальным порогом лучший кандидат
поздней стадии выходил «93% мёртвых», с порогом стадии — 0–7%.

**Перед показом гнать таблицу по всем шотам: `рука ср · доля мёртвых · тряска max`.**
Двух проходов хватает, чтобы поймать оба класса брака сразу. Исключение — шот «готовая
работа, рука ушла»: у него 94% мёртвых по построению, это не дефект, а фиксация итога.

## Закрывашка с человеком — двигать CTA, иначе текст ложится на лицо

Дефолт `y=385` рассчитан на закрывашку-доску. Если в кадре человек, эта высота приходится
ровно на лицо (правка заказчика: «текст перекрывает лицо человека»). В сборщике для этого нужна отдельная переменная высоты CTA: ставить **150** —
верх кадра, там обычно чистая стена. Низ (`1560+`) хуже: там пестрит пол и мешает интерфейс Instagram.

## Кадрировать МОЖНО и на вертикальном исходнике

«`rotation=90`, кадр уже 9:16, кадрировать нечего» — верно про формат, но не про
композицию. Если сбоку в кадр лезет лишнее (в открывашке справа был коридор
с чужой картиной, которую заказчик прочёл как руку), из нативных 2160×3840 берётся окно
поуже и апскейлится: запас четырёхкратный, потери нет.

```json
{"src":"A001","ss":6.9,"d":1.9,"zoom":0,"frame":"1620:2880:0:400"}
```
Поле `frame` в `cut.json` — необязательный кроп `W:H:X:Y` из нативного кадра
(соблюдать 9:16), дальше всё как обычно. Побочная польза: предмет становится крупнее,
а открывашке это идёт.
